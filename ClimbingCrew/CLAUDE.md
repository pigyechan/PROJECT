# 클라이밍 크루 관리 서비스

## 프로젝트 개요

클라이밍 크루를 관리하는 웹 서비스. 이직용 포트폴리오 프로젝트.

향후 모바일 앱 확장을 염두에 두되, **API는 클라이언트 종류와 무관하게 설계**한다.
서버는 JSON만 반환하고, 화면은 그 소비자일 뿐이라는 원칙을 지킨다.

## 개발자 컨텍스트

- C# 3년 경력, 반도체 협력사 재직
- Java는 초급 단계 (클래스 작성 가능, 인터페이스는 문법만 알고 쓰임새 미숙)
- Java/Spring 채용 공고를 확인하고 스택 전환 결정
- 준비 기간 6개월 (2026년 8월 ~ 2027년 1월)

### 도움받을 때 원하는 방식

- 정답을 바로 주기보다 **질문과 힌트로 스스로 답을 찾게** 유도
- 시니어 개발자 멘토처럼 설계 의도를 먼저 묻기
- 진도는 완성한 기능 단위로, 작은 단위로 매일. 시간 압박 없이

## 기능 요구사항

### 개인 화면
- 자신이 가입한 크루 목록 확인
- 다녀온 암장을 지도에 핀으로 기록 (네이버 지도 API 사용)
- 핀 클릭 시 본인이 남긴 평 조회
- 암장 기록/평을 크루원들과 공유

### 크루 화면
- 달력으로 크루원들이 참여하는 모임을 한눈에 확인

## 도메인 설계

### 엔티티

`User` / `Crew` / `CrewMember` / `Gym` / `Review` / `Event` / `EventAttendee`

### 핵심 설계 결정

**역할은 사용자가 아니라 가입 관계에 붙는다**

한 사람이 A크루에서는 OWNER, B크루에서는 MEMBER일 수 있다.
따라서 `User.role`이 아니라 `CrewMember.role`로 표현한다.

```java
enum CrewRole { OWNER, MANAGER, MEMBER }
```

**암장은 독립 엔티티로 분리한다**

여러 사용자가 같은 암장을 방문해도 중복 저장하지 않는다.
`Gym`(장소 정보, 좌표)과 `Review`(누가, 언제, 뭐라고)를 분리해
"이 암장에 우리 크루원 N명이 평을 남김" 같은 조회가 가능하도록 한다.

암장 데이터는 네이버 지도 API를 통해 가져온다.

**리뷰 공개 범위는 enum으로 표현한다**

```java
enum Visibility { PUBLIC, CREW_ONLY, PRIVATE }
```

- 기본값은 `PUBLIC`
- `CREW_ONLY`는 **"내가 속한 모든 크루"** 를 의미한다 (특정 크루 한정 아님)
- boolean 대신 enum을 쓴 이유: 나중에 "선택한 크루만" 요구가 생기면
  값 추가만으로 확장할 수 있다

> 향후 특정 크루 한정이 필요해지면 `ReviewShare(reviewId, crewId)` 조인 테이블을
> 추가하고 `SELECTED_CREWS` 값을 넣는다. 단 조회 시 N+1 문제에 주의.

**모임 생성 권한은 역할로 표현한다**

권한 플래그(`canCreateEvent`) 방식이 아니라 역할(`OWNER`/`MANAGER`)로 구분한다.
권한이 늘 때마다 컬럼이 늘어나는 것을 피하기 위함.

- 모임 생성 가능: OWNER, MANAGER
- MANAGER 임명 가능: OWNER만

### 무결성 규칙

**OWNER는 크루당 정확히 1명**

"OWNER 없는 크루"라는 유령 데이터가 생기지 않도록 강제한다.

**크루 탈퇴**
- OWNER는 다른 사람에게 OWNER를 넘긴 뒤에야 탈퇴 가능
- 단, 크루원이 OWNER 혼자뿐이면 크루 삭제 가능 (넘길 사람이 없어 갇히는 것을 방지)

**회원 탈퇴**
- OWNER인 크루가 있으면 모두 넘겨야 함
- 혼자만 있는 크루는 삭제 처리
- MVP 범위에서 제외 가능

**크루 삭제 시 연쇄 처리**
- 해당 크루의 `Event`, `EventAttendee` 는 함께 삭제 (cascade)
- `Review`는 삭제하지 않음 — 리뷰의 주인은 크루가 아니라 개인
  (`CREW_ONLY`였던 리뷰는 볼 사람이 없어지지만 그대로 둔다)

## 학습 & 개발 방식 (2026-08-12 확정)

### 원칙

- **JIT(Just-In-Time) 학습**: 강의를 순서대로 완주하지 않는다. 서버를 먼저 만들고, 막히는 부분만 그때그때 강의/문서에서 찾아본다.
- **Walking Skeleton**: 자바 문법을 다 떼고 나서 스프링을 시작하는 게 아니라, 최소 동작하는 Spring Boot 서버 + 작은 CRUD부터 시작해서 점점 키운다. `Crew` 단일 테이블 CRUD(관계 없음, Controller→Service→Repository)가 첫 걸음.
- 자바 순수 문법(C#과 겹치는 부분)은 최소화하고, 인터페이스/제네릭/컬렉션/예외 등 실제 약점 위주로 강의를 발췌한다. Repository 인터페이스처럼 실제 코드에서 마주치는 순간에 인터페이스 개념을 익히는 것을 우선한다.
- 시간 배분은 하루 단위로 고정하지 않고 **주 단위 평균**으로 유연하게 조정한다. 새롭고 어려운 개념을 만난 날은 이해에 더 쓰고, 다음 날 프로젝트로 몰아서 보충해도 된다.
- 도메인 세부 결정(크루 가입 방식, RSVP 상태값 등)은 미리 다 정하지 않고, 실제로 그 기능을 구현할 때 대화하면서 정한다.

### 세 트랙 & 시간 예산

- **프로젝트(메인)** — 백엔드 CRUD를 키워가며, 기능이 완성되는 대로 화면(순수 HTML+CSS+JS)도 같이 확장. 화면은 Claude가 구현, mock 데이터 단계 없이 실제 API에 바로 연결.
- **코딩테스트** — 프로그래머스, 대기업/대형 서비스기업 전형 대비. 매일 2시간 지속(감 유지가 목적이라 몰아서 하지 않음). 2026-08-12 기준 기초 60문제를 그 주 안에 스퍼트로 마무리 예정.
- **강의** — JIT로 필요할 때만.
- 평일 기본 8시간 확보 가능(면접준비/신문스크랩 등 고정 시간 포함), 주말 4시간 × 2일.
