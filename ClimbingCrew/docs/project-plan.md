# ClimbingCrew — 프로젝트 계획

## 배경

- 목표: 스프링 부트 백엔드를 직접 구현해서, 실제로 구동되는 프로그램을 처음부터 끝까지 만들어본다.
- 학습자 배경: 2년차 개발자, C#/.NET Framework + Oracle DB 실무 경험 있음. 서버(백엔드) 개발은 처음.
- Java 백엔드 툴체인(Gradle, JUnit5, Mockito, AssertJ, Cucumber-JVM)은 `TicketService` kata를 통해 별도로 익히는 중 (Grit_Project 커리큘럼, C-3 헥사고날 설계 등과 병행).
- 디자인/프론트엔드 비주얼 작업은 이 프로젝트의 학습 목표가 아니라서, 필요할 때 별도로 지원받아 최소한으로만 구성하고 학습 시간은 백엔드 로직에 집중한다.

## 도메인

**클라이밍 크루 관리 + 크루원 간 중고 장비 경매**

- 크루원 명단을 관리한다.
- 크루원들끼리 중고 클라이밍 장비(신발, 초크백 등)를 경매 형태로 거래한다.

경매 도메인을 고른 이유: "여러 사람이 같은 순간에 같은 자원(최고 입찰가)을 놓고 경쟁"하는 구조라서, 예약형 도메인보다도 동시성 문제가 뚜렷하고, 마감 임박 시 입찰이 몰리는 현상("sniping")이 3개월차 대용량 트래픽 학습과 자연스럽게 이어진다.

## 전체 로드맵 (3개월)

| 개월차 | 주제 | 내용 |
|---|---|---|
| 1 | 계획 + 골격 + 기본 CRUD | 스프링 부트 walking skeleton, `Member`/`AuctionItem` 각각 독립적인 단일 테이블 CRUD |
| 2 | 백엔드 API 심화 (JPA) | `Bid` 엔티티 추가, 엔티티 간 연관관계, 트랜잭션, 검증/예외 처리 |
| 3 | 대용량 트래픽 + 인프라 | 동시 입찰 처리(락), 마감 임박 트래픽 처리(캐싱, 큐), 배포/모니터링 노출 학습 |

### 1개월차 — 계획 + 골격 + 기본 CRUD

**설계 원칙**: 이 규모(테이블 1~2개, 관계 없음)에는 별도 아키텍처 패턴(SOLID 원칙을 넘어선 계층 분리, 헥사고날 등)이 필요 없다. `Controller → Service → Repository → Entity`의 기본 레이어드 구조로 충분하다. TicketService kata에서 다루는 SOLID/헥사고날은 "결제 수단이 늘어나는" 것처럼 변경이 실제로 반복될 때 필요해지는 것이지, 처음부터 미리 끌어올 필요는 없다. (GOOS의 walking skeleton 원칙과 동일한 맥락 — 완성형을 미리 설계하지 않고, 가장 얇게라도 실제로 도는 것부터 만든다.)

- **1주차**: 스프링 부트 프로젝트 생성. 엔드포인트 1개(`GET /health` 등)가 실제로 응답. Oracle DB 연결 확인(쿼리 없이 연결만).
- **2주차 이후**: 아래 두 엔티티를 각각 독립적으로 CRUD.

**`Member` (크루원)**

| 필드 | 타입 | 의미 |
|---|---|---|
| `id` | Long | 기본키 |
| `name` | String | 이름 |
| `contact` | String | 연락처 |
| `joinDate` | Date | 크루 가입일 |
| `level` | String | 클라이밍 등급 |
| `memo` | String | 자유 메모 |

**`AuctionItem` (경매 물품)**

| 필드 | 타입 | 의미 |
|---|---|---|
| `id` | Long | 기본키 |
| `title` | String | 물품명 |
| `description` | String | 설명 |
| `startPrice` | Integer | 시작가 |
| `endsAt` | DateTime | 마감 시각 |

CRUD 데모 (겉으로 보이는 동작): 크루원 목록/등록/수정/탈퇴, 경매 물품 목록/등록/수정/삭제 — 아직 입찰 기능 없음, 두 엔티티는 서로 참조하지 않음.

**참고 — soft delete**: 크루원 "탈퇴" 처리를 지금은 실제 삭제(hard delete)로 해도 무방하다. 2개월차에 `Bid`가 `Member`를 참조하기 시작하면, 탈퇴한 크루원의 과거 입찰 기록이 깨지지 않도록 "삭제 대신 비활성화(`active=false`)" 방식으로 전환을 검토한다.

### 2개월차 — 백엔드 API 심화 (JPA)

- `Bid` (입찰) 엔티티 추가: 물품(`AuctionItem`), 입찰자(`Member`), 금액, 입찰 시각.
- `AuctionItem` ↔ `Member` ↔ `Bid` 사이 연관관계 등장 (N:1 관계 2개).
- "새 입찰가는 현재 최고가보다 높아야 한다" 같은 도메인 검증 로직.
- 여러 작업이 하나로 묶여야 하는 지점에서 트랜잭션(`@Transactional`) 학습.
- 팀그릿 독서(JPA 강의)와 병행.

### 3개월차 — 대용량 트래픽 + 인프라

- **동시성 문제**: 두 명이 거의 동시에 입찰하면 순서를 어떻게 보장할지 (낙관적 락/버전 관리, 비관적 락, 또는 Redis 분산 락).
- **트래픽 스파이크**: 마감 임박 시 입찰이 몰리는 상황("sniping") 처리 — 캐싱(현재 최고가 조회), 큐잉.
- **인프라 노출 학습**: 배포, 모니터링. (이 단계는 "직접 겪어서 필요성을 체감하며 개발"하기보다 "개념을 익히고 작은 규모로 흉내 내보는" 노출 학습 수준으로 기대치를 잡는다.)
- Grit 커리큘럼의 "팀그릿" 독서(ai-backend-guide Ch10~11 인프라·배포)와 시기적으로 맞물린다.
