# D-5: AI 파이프라인 (글쓰기 하네스 v1 + 스피치 리허설 에이전트)

## 1. 글쓰기 하네스 v1

`Blog_Writer`(Phase 0/T8)의 Gen→Critique→Eval→Refine 하네스 v0를 에세이·전달 도메인으로 확장했다. 새 Python 자동화를 짜는 대신, Claude Code의 서브에이전트(Agent)를 "새 세션"으로 실제 활용했다 — Critique/Eval을 이 대화 맥락을 전혀 모르는 독립된 에이전트로 띄워서, 글이 어떻게(AI 도움 여부 포함) 쓰였는지 모르는 상태로 판정하게 했다.

**구성 파일**: [`docs/d5-writing-harness/`](d5-writing-harness/) — 구조·v0 대비 변경점·재실행 절차는 [`README.md`](d5-writing-harness/README.md) 참고
- `rubric.yaml` — 4축(message_clarity, four_step_fidelity, no_fluff, reader_alignment), 가중치 합 1.0, min_total 3.0
- `gen_system.md` — 초안 생성 시 저자 재료 밖 내용을 지어내지 않는다는 규칙
- `critique_system.md` — "저자 영역 침범 금지" 규칙을 명시(허용/금지 예시 포함), 약점 정확히 3개, axis는 rubric 4개 중에서만
- `eval_system.md` — Critique 결과를 미리 보지 않고 독립적으로 채점 (Test_Writer(1-1) "관대한 그린" 재발 방지)
- `refine_system.md` — 저자가 채택한 지적만 반영, 기각된 지적은 건드리지 않는다는 규칙

v0(Blog_Writer) 대비 진짜 고도화 지점은 축 개수 조정이 아니라, **"저자 영역 침범 금지" 규칙을 Gen·Critique·Refine 세 프롬프트 모두에 처음으로 명시했다는 것**이다. v0는 마케팅 블로그 도메인이라 이 경계가 필요 없었지만, 개인 경험·판단이 핵심인 에세이 도메인으로 확장하면서 새로 필요해졌다.

## 2. D-2/D-3 실행 결과 + 채택/기각 로그

두 글 모두 Critique(3건)·Eval(4축 점수) 각각 독립된 서브에이전트로 실행했다. 상세 로그는 각 문서에 있다.

- [`d2-technical-essay.md`](d2-technical-essay.md) — Eval 가중합 3.2 PASS. Critique 3건 중 2건 채택(반영 완료: "증거/관찰"과 "검증"의 중복 제거), 1건 기각(제목의 사건성과 본문 가정법 서술 간극 — 과장 없이 정직하게 쓴 선택으로 판단).
- [`d3-growth-essay.md`](d3-growth-essay.md) — Eval 가중합 3.0(턱걸이) PASS. Critique 3건 중 2건 채택(반영 완료: 독자용 메시지 추가, 한계 인정 문단 재배치), 1건 기각(반복이 5회 이상이 아니라 감점할 만큼 심각하지 않다고 판단).

**"관대한 그린" 재발 여부**: 재발하지 않았다. D-2에서 Eval의 낮은 점수(no_fluff 2, reader_alignment 2)가 Critique의 실제 지적과 방향이 일치했다. 다만 Critique는 반복 문제를 four_step_fidelity(단계 경계 문제)로 분류한 반면 Eval은 그 축에 4점을 줘서, 같은 문제를 서로 다른 축에 걸어놓은 **axis 분류 불일치**는 있었다 — 완전한 모순은 아니지만 하네스 설계에서 axis 경계가 명확하지 않을 수 있음을 보여주는 사례로 기록해둔다.

**2차 재검증(Refine 후 재실행)**: Refine을 적용한 뒤 같은 하네스를 다시 돌렸다.
- D-2: 가중합 3.2 → 3.6 (순수 개선, no_fluff 2→4)
- D-3: 가중합 3.0 → 3.0 (**총점은 그대로였지만, reader_alignment 2→3 개선과 no_fluff 4→3 악화가 상쇄됨**) — reader_alignment를 고치려고 추가한 독자용 문단이 4단계 구조에 소속되지 않은 채 끼어들면서 four_step_fidelity를 건드렸고, 반복되던 "관점을 얻었다"는 표현을 한 번 더 반복시켜 no_fluff를 깎아먹었다. 한 축을 고치는 수정이 다른 축에 새 문제를 만들 수 있다는 걸 실제로 확인했고, 이 하네스가 "한 번 돌리고 끝"이 아니라 "고친 뒤 재검증까지 포함해야 하는" 이유가 여기서 나왔다. D-3는 이 발견을 반영해 문단을 "다음 단계" 섹션에 명확히 편입시키고 중복 문장 하나를 삭제하는 재조치까지 완료했다.

## 3. 스피치 리허설 에이전트

D-4의 스피치 녹화 전사(transcript)와 녹화 길이(초)를 입력받아, 필러 워드 빈도·말 속도·구조(도입-핵심-예시-마무리)를 피드백하는 에이전트.

**구성 파일**: [`docs/d5-speech-harness/`](d5-speech-harness/) — 구조·재실행 절차는 [`README.md`](d5-speech-harness/README.md), 시스템 프롬프트는 [`rehearsal_agent_system.md`](d5-speech-harness/rehearsal_agent_system.md). "저자 영역 침범 금지"를 여기서는 "발표 내용(메시지·논리)에 의견을 내지 않고, 전달 방식(delivery)만 다룬다"로 구체화했다.

**실제 실행 결과** (3~5분 스피치, 녹화 3분 17초): 글쓰기 하네스와 동일하게 이 대화 맥락을 모르는 독립 서브에이전트로 실행했다.
- 필러 워드: "그" 2회, "그러니까" 1회, "뭐" 1회 → 총 4회(분당 1.22회)
- 말 속도: 분당 265자(일반 범위 250~350자 안, 느긋한 편)
- 구조: 4단계 모두 실제 문장으로 확인됨
- **에이전트가 새로 발견한 지점**: 예시→마무리 전환에 "정리하면" 같은 전환 문구가 없다는 지적 — 이건 자가 점검(3번 섹션)에서 본인이 "뒤로 갈수록 조급해졌다"고 느낀 것과 독립적으로 일치한 결과다. 상세 로그는 [`d4-speech-delivery.md`](d4-speech-delivery.md) 참고.

**처음에 겪은 시행착오**: 처음엔 이 분석을 서브에이전트 없이 이 대화 안에서 직접 했었는데, 사용자가 "이게 진짜 에이전트냐"고 지적해서 재점검했다 — 글쓰기 하네스처럼 격리된 서브에이전트로 다시 실행했다. 필러 워드 검출 결과("그" 2회를 처음엔 놓쳤음)와 구조 지적(전환 문구 누락)이 직접 분석 때보다 더 정확하고 풍부했다 — 이번에도 "본인이 만든 게 진짜 격리됐는지" 확인하는 절차 자체가 결과 품질에 영향을 준 사례다.

## 4. AI가 저자 영역을 넘보려 한 사례 (또는 없었던 이유, 최소 300자)

이번 파이프라인 운영에서는 AI(Critique/Eval)가 저자 영역(메시지·논리)을 침범한 사례를 발견하지 못했다. D-2/D-3 각각 1차·2차, 총 4번의 Critique 실행 전체에서 fix_hint를 확인했는데, 전부 "무엇을 보강해야 하는지" 방향만 제시했고, "이렇게 고치세요"라며 완성된 문장을 대신 써준 사례는 하나도 없었다. 예를 들어 D-3의 reader_alignment 지적에서 fix_hint는 "독자층에게 어떤 구체적 쓸모를 주는지 명시하는 문장을 추가하라"는 방향만 제시했을 뿐, 실제로 어떤 문장을 쓸지는 제안하지 않았다. 그 문장(뼈대 비유)은 본인이 직접 만들었다.

2차 재검증에서도 같은 패턴이 반복됐다는 점이 특히 의미 있다. 2차 Critique는 1차 수정으로 새로 생긴 문제(D-3의 문단 소속 불명, 반복 심화)까지 정확히 지적했지만, 이번에도 "문단을 어디로 옮겨야 하는지" 방향만 제시("재해석 단계 또는 다음 단계 중 어느 쪽에 속하는지 명시적으로 재배치")했을 뿐, 옮긴 뒤의 실제 문장을 대신 써주지는 않았다. 즉 AI가 반복적으로 개입할 기회(1차, 2차)가 주어져도 경계를 유지했다.

AI가 저자 영역을 넘지 않은 이유는, `critique_system.md`(그리고 새로 추가한 `gen_system.md`, `refine_system.md`) 프롬프트에 "저자 영역 침범 금지" 규칙을 명시적으로 넣고 허용 예시와 금지 예시를 나란히 제시해서 AI가 방향과 완성 문장의 경계를 헷갈리지 않게 했기 때문이라고 판단한다. 또한 Critique/Eval을 이 대화의 맥락을 전혀 모르는 독립된 서브에이전트로 매 라운드 새로 분리해서 실행한 것도, AI가 "저자가 원할 법한 문장"을 추측해서 대신 채워 넣을 유인 자체를 줄이는 데 도움이 됐다고 본다.
