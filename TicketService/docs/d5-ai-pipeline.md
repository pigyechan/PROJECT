# D-5: AI 파이프라인 (글쓰기 하네스 v1 + 스피치 리허설 에이전트)

## 1. 글쓰기 하네스 v1

`Blog_Writer`(Phase 0/T8)의 Gen→Critique→Eval→Refine 하네스 v0를 에세이·전달 도메인으로 확장했다. 새 Python 자동화를 짜는 대신, Claude Code의 서브에이전트(Agent)를 "새 세션"으로 실제 활용했다 — Critique/Eval을 이 대화 맥락을 전혀 모르는 독립된 에이전트로 띄워서, 글이 어떻게(AI 도움 여부 포함) 쓰였는지 모르는 상태로 판정하게 했다.

**구성 파일**: `docs/d5-writing-harness/`
- `rubric.yaml` — 4축(message_clarity, four_step_fidelity, no_fluff, reader_alignment), 가중치 합 1.0, min_total 3.0
- `critique_system.md` — "저자 영역 침범 금지" 규칙을 명시(허용/금지 예시 포함), 약점 정확히 3개, axis는 rubric 4개 중에서만
- `eval_system.md` — Critique 결과를 미리 보지 않고 독립적으로 채점 (Test_Writer(1-1) "관대한 그린" 재발 방지)

## 2. D-2/D-3 실행 결과 + 채택/기각 로그

두 글 모두 Critique(3건)·Eval(4축 점수) 각각 독립된 서브에이전트로 실행했다. 상세 로그는 각 문서에 있다.

- [`d2-technical-essay.md`](d2-technical-essay.md) — Eval 가중합 3.2 PASS. Critique 3건 중 2건 채택(반영 완료: "증거/관찰"과 "검증"의 중복 제거), 1건 기각(제목의 사건성과 본문 가정법 서술 간극 — 과장 없이 정직하게 쓴 선택으로 판단).
- [`d3-growth-essay.md`](d3-growth-essay.md) — Eval 가중합 3.0(턱걸이) PASS. Critique 3건 중 2건 채택(반영 완료: 독자용 메시지 추가, 한계 인정 문단 재배치), 1건 기각(반복이 5회 이상이 아니라 감점할 만큼 심각하지 않다고 판단).

**"관대한 그린" 재발 여부**: 재발하지 않았다. D-2에서 Eval의 낮은 점수(no_fluff 2, reader_alignment 2)가 Critique의 실제 지적과 방향이 일치했다. 다만 Critique는 반복 문제를 four_step_fidelity(단계 경계 문제)로 분류한 반면 Eval은 그 축에 4점을 줘서, 같은 문제를 서로 다른 축에 걸어놓은 **axis 분류 불일치**는 있었다 — 완전한 모순은 아니지만 하네스 설계에서 axis 경계가 명확하지 않을 수 있음을 보여주는 사례로 기록해둔다.

## 3. 스피치 리허설 에이전트

D-4의 3~5분 스피치 녹화 전사(transcript)를 입력받아, 필러 워드(음/어/그) 빈도·말 속도·구조(도입-핵심-마무리)를 피드백하는 에이전트.

**상태**: 프롬프트 설계까지 완료, 실제 실행은 D-4 녹화 완료 후 진행 예정 (아직 전사할 녹화 자체가 없음).

**프롬프트 설계(안)**:
> 당신은 스피치 코치입니다. 아래 전사(transcript)를 보고: ① "음", "어", "그", "그러니까" 같은 필러 워드의 총 횟수와 분당 빈도, ② 전체 발화 시간 대비 글자 수로 추정한 말 속도, ③ 도입-핵심-예시-마무리 4단계가 전사에서 실제로 구분되는지(각 단계 시작 지점을 인용해서), 이 3가지를 피드백하세요. 대본을 대신 써주지 마세요 — 무엇이 부족한지만 짚습니다.

## 4. AI가 저자 영역을 넘보려 한 사례 (또는 없었던 이유, 최소 300자)

이번 파이프라인 운영에서는 AI(Critique/Eval)가 저자 영역(메시지·논리)을 침범한 사례를 발견하지 못했다. Critique의 fix_hint를 D-2/D-3 두 번의 실행 전체에서 확인했는데, 전부 "무엇을 보강해야 하는지" 방향만 제시했고, "이렇게 고치세요"라며 완성된 문장을 대신 써준 사례는 하나도 없었다. 예를 들어 D-3의 reader_alignment 지적에서 fix_hint는 "독자층에게 어떤 구체적 쓸모를 주는지 명시하는 문장을 추가하라"는 방향만 제시했을 뿐, 실제로 어떤 문장을 쓸지는 제안하지 않았다. 그 문장(뼈대 비유)은 본인이 직접 만들었다.

AI가 저자 영역을 넘지 않은 이유는, `critique_system.md` 프롬프트에 "저자 영역 침범 금지"라는 규칙을 명시적으로 넣고 허용 예시와 금지 예시를 나란히 제시해서 AI가 방향과 완성 문장의 경계를 헷갈리지 않게 했기 때문이라고 판단한다. 또한 Critique를 이 대화의 맥락을 전혀 모르는 독립된 서브에이전트로 분리해서 실행한 것도, AI가 "저자가 원할 법한 문장"을 추측해서 대신 채워 넣을 유인 자체를 줄이는 데 도움이 됐다고 본다.
